### Behavioral vs. Static Verification (explicit split, per prompt's request)

- **Genuinely behaviorally verified**: the actual duplicate-rejection semantics of all three partial indexes, executed against a real SQLite engine (`sqlite:///:memory:`, `session.commit()`, catching real `IntegrityError`) — `test_duplicate_department_assignment_is_rejected`, `test_duplicate_location_assignment_is_rejected`, `test_duplicate_director_assignment_is_rejected` all pass, and the two non-collision tests (`test_same_user_can_have_department_and_director_assignment_together`, `test_different_users_can_share_the_same_department_assignment`) prove the indexes are correctly scoped (not accidentally global). **This is a materially stronger result than the CHECK-constraint SQLite proxy used in 3.3**: Python 3.14's bundled SQLite (≥3.8.0) supports partial indexes (`CREATE INDEX ... WHERE ...`) with the same semantics as Postgres for this exact pattern, and this was independently confirmed by compiling the same `Index` objects through both `sqlalchemy.dialects.sqlite.dialect()` and `sqlalchemy.dialects.postgresql.dialect()` and diffing the output — the generated DDL is byte-for-byte identical apart from dialect labeling: `CREATE UNIQUE INDEX uq_user_scope_assignments_department ON user_scope_assignments (user_id, department_id) WHERE department_id IS NOT NULL` (same for `_location`/`_director`). Because the DDL text and the WHERE-clause partial-uniqueness mechanism are identical between the two dialects for this pattern, the SQLite runtime proof is a valid behavioral proxy for Postgres here — unlike, say, dialect-specific expression indexes or `NULLS NOT DISTINCT` syntax, which would NOT transfer.
- **Statically reviewed only (no live Postgres instance in this sandbox — same limitation as 3.3-3.5)**: the migration's `op.create_index(..., postgresql_where=sa.text(...))` calls were verified via `alembic upgrade 202606101200:202606151200 --sql` (offline SQL generation) — confirmed the exact expected DDL: `CREATE UNIQUE INDEX uq_user_scope_assignments_department ON user_scope_assignments (user_id, department_id) WHERE department_id IS NOT NULL;` (and the two siblings), emitted in the correct position after `CREATE TABLE user_scope_assignments (...)`. The offline run still hits the same pre-existing, expected `AttributeError` on the data-driven reclassification loop later in `upgrade()` (unrelated to this change — a known `--sql` dry-run limitation for data-driven migrations, documented in the prior slice). `alembic downgrade 202606151200:202606101200 --sql` completed cleanly end-to-end (no data loop in `downgrade()`), confirmed all three `DROP INDEX` statements appear in the correct order before `DROP TABLE user_scope_assignments`. **Recommend the same staging-DB dry run already recommended for 3.3-3.5** (`alembic upgrade head` against a seeded copy) to get true Postgres runtime proof of this exact migration, since `postgresql_where` is a Postgres-only dialect kwarg (silently ignored on other backends `alembic` might theoretically target, though this project is Postgres-only in practice).
