## Task 4.3a Evidence (this apply call)

**Scope**: task 4.3a only (new task inserted ahead of 4.3, per maintainer decision) — expose the current user's granted permission codes via `/auth/me`. No frontend code touched in this call, per explicit constraint.

### Investigation (read before writing, not assumed)

- `backend/app/schemas/user.py`'s `UserResponse` (`/auth/me`'s prior `response_model`): only `role: UserRole`, no permission codes anywhere.
- `backend/app/api/deps.py`'s `get_current_user()`: already eager-loads `selectinload(User.user_roles).selectinload(UserRoleAssignment.role).selectinload(Role.permissions)` for every authenticated request (Phase 1 work) — the data needed was already in memory; no new query required.
- `backend/app/api/v1/endpoints/users.py`'s `list_users`/`update_user`/etc.: all query `select(User)` with **no** eager-load of `user_roles -> role -> permissions`. Since `UserResponse` is also this router's `response_model` (list + single), adding a `permissions` field directly to `UserResponse` would either raise a lazy-load error in FastAPI's async context or force an N+1 query per listed user. **Decision**: dedicated `AuthMeResponse(UserResponse)` subclass, used only by `/auth/me`, not the shared schema.
- `backend/app/api/deps.py`'s `has_permission()`/`is_bootstrap_admin()`: `has_permission()` unconditionally returns `True` for the hidden bootstrap `ADMIN` account (identified by `bootstrap_admin_email`) regardless of any `role_permissions` row — a code-level bypass, not DB-backed. `DEV` gets **no** such bypass in `has_permission()`; DEV's access is entirely DB-backed via `role_permissions`, same as every other role.
- `backend/alembic/versions/202606101200_canonical_rbac_roles.py`: seeds an unfiltered `role_permissions` cross-join granting **every** existing permission code to the `ADMIN` and `DEV` roles at migration time, and every subsequent permission-adding migration in this change (`202606161200`, `202606181200`, `202606191200`) mirrors that same grant-to-`ADMIN`/`DEV` convention (confirmed by reading each, not assumed from the migration filenames alone).

### Bootstrap ADMIN/DEV decision (explicit, per prompt's request)

`permission_codes_for_user()` does **not** special-case bootstrap `ADMIN` with a synthetic "all permissions" sentinel. It uses the exact same DB-backed `user.user_roles -> role -> permissions` flattening for every user, including bootstrap `ADMIN` and `DEV`. This is consistent with `has_permission()`'s actual enforcement **as long as this codebase's own migration convention holds** (every new permission code granted to `ADMIN`/`DEV` via `role_permissions`) — which it has, in every migration in this change so far. The alternative (querying `SELECT DISTINCT code FROM permissions` for bootstrap `ADMIN` to literally mirror its unconditional code-level bypass) was rejected: it would require a new DB query (violating this task's explicit constraint) and would produce an opaque, unauditable "the whole catalog, no matter what's actually granted" list that no longer reflects real `role_permissions` rows at all. The docstring on `permission_codes_for_user()` documents this explicitly as a known, non-silent gap: *if* a future migration ever adds a permission without also granting it to `ADMIN`/`DEV`, this list would under-represent bootstrap `ADMIN`'s actual (unconditional) access. `DEV` needed no such caveat — its access was already 100% DB-backed with no bypass to diverge from.

### Deferred: CATEDRATICO self check-in / SECRETARIA reads (architectural gap, not an oversight)

**Not implemented in this call** (flagged per the prompt's own explicit instruction to stop at a natural boundary rather than push through under budget pressure):

- `CATEDRATICO` self check-in restricted to own `employee_id` via `attendance.mark.self`.
- `SECRETARIA` catedrático-scoped attendance reads (design.md's Corrected Role Matrix lists `SECRETARIA: Attendance reports = read`, but neither the spec's "Administrative Attendance Access" requirement text nor task 3.12's literal scope text names `SECRETARIA` for attendance-report reads — only for employee writes, already covered by task 3.9. This migration deliberately does **not** grant `SECRETARIA` `attendance.view`. This is a real design.md-vs-spec inconsistency, flagged here rather than resolved by assumption, per "don't over-build.")

**Why CATEDRATICO self check-in was not implemented**: `check_in`/`check_out` (`POST /attendance/check-in`, `POST /attendance/check-out`) are the *only* attendance-marking endpoints in this codebase. They are:
- Completely unauthenticated by design (`"No requiere autenticación. El rostro en las imágenes es la credencial."` — explicit in the pre-existing docstring), intended as a physical shared-kiosk face-recognition flow.
- Driven entirely by face-embedding match — `AttendanceCheckIn`/`AttendanceCheckOut` (`backend/app/schemas/attendance.py`) have **no `employee_id` field at all**. The "target employee" is discovered by `face_service.find_best_match(db, query_embedding)`, never supplied by the caller.

The spec's "CATEDRATICO marks own attendance" scenario ("GIVEN an authenticated actor has CATEDRATICO... THEN allow when it targets the actor's own employee identity, AND deny if it targets a different employee's attendance record") presupposes an *authenticated* actor whose identity can be compared against a *targeted* employee. Neither precondition exists in the current endpoint shape: there is no caller identity (no auth dependency) and no caller-specified target (no `employee_id` param) to compare against. Implementing this scenario requires one of:
1. **Force authentication onto `check_in`/`check_out`** — but this breaks the intentional anonymous kiosk UX (a shared physical device could no longer let arbitrary employees tap-and-scan without each first obtaining a personal JWT), and no design.md decision row (D1-D10) authorizes removing that capability.
2. **Add optional authentication** (only enforce self-scope when a bearer token happens to be present) — a real, non-trivial architecture addition (a new `get_optional_current_user`-style dependency, decode-failure-swallowing semantics, an `assert_object_access(actor, employee_id=matched_employee.id)` call after the face match) that design.md does not specify and that materially changes the endpoint's security model. Given the explicit budget/scope discipline requested for this call and that this is a genuine, unreviewed design decision rather than a mechanical gate swap, it was not implemented here.
3. **A separate, new authenticated self-check-in endpoint** (no face recognition, just JWT + `current_user.employee_id`) — this doesn't exist in the frontend (`frontend/src/app/core/services/attendance.service.ts` only calls `/attendance/check-in`, `/attendance/check-out`, `/attendance/today`, `/attendance`) or backend today, and would be new endpoint surface beyond "gate replacement," which is out of this task's stated scope ("`DECANO`/.../`COORDINADOR` read-only reports... `CATEDRATICO` self check-in via `attendance.mark.self` restricted to own `employee_id`" reads as *gating an existing capability*, not building a new one).

`attendance.mark.self` (seeded, ungranted, since task 3.5) remains ungranted to any role — granting it now without a matching enforcement call site would be an inert, unverifiable change; the established convention in this codebase (`202606161200`/`202606171200`) ties each permission-grant migration to the specific endpoint wiring it enables, and I did not want to seed a grant this call cannot prove is enforced anywhere.

**Recommend**: a maintainer decision on which of the three options above (or another) is intended, ideally recorded as a new design.md decision row (a D11), before the next apply call implements this. This is the natural split point for the next slice.

1. **Resolving "the request's scope DIRECTOR"** (needed because a facultad/sede can have more than one `DIRECTOR` scoped to it, and the spec's Stage 2 scenario just says "the request's scope DIRECTOR", singular): `_resolve_scope_director_ids(db, employee)` queries `user_scope_assignments` for rows whose `department_id`/`location_id` matches the request's employee (OR-match across both columns, mirroring 3.7's already-committed `assert_request_scope` union-match convention for facultad-vs-sede), then filters to the subset of those rows whose `user` actually holds the `DIRECTOR` canonical role (via the existing `user_has_role` predicate) — returning a **set**, not a single ID, because design.md's own D4 explicitly supports 1:N here too ("director→facultad/sede (notifications)... supports 1:N").

3. **Fail-closed for both unresolved cases**: if step 1 resolves to an empty set (no `DIRECTOR` is scoped to this request's facultad/sede at all — an administrative-data gap, not a security exception), stage 2 is denied for every actor, matching design.md's own "Any unresolved link fails closed (403), never falls back to global access."
